# cutover: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make history quiet in Bugsink before anything files from it. Every fingerprint whose almanac issues are all closed on GitHub gets resolved in Bugsink, with a comment that links the closed issues, so a fix that later fails shows up as a regression. Fingerprints with an open almanac issue stay unresolved for the worker.

**Program plan:** `docs/superpowers/plans/2026-11-09-error-tracker.md`, step `cutover`.

**Architecture:** A `cutover` verb in the brined-almanac binary, next to `sync-check`. `src/cutover.rs` holds pure functions (body to grouping key, the plan, the comment) and two thin HTTP clients (GitHub issues, Bugsink's canonical API). `scripts/cutover` runs it with secrets from 1Password. Dry run by default, `--apply` resolves and comments.

**Why a Rust verb, not a script:** the fingerprint comes from Rust (`bugsink::event` builds `[service, tool, class]`, and `tool_failures::facts` writes the body the script reads back). Keeping the parser beside them lets one test pin the round trip from filer body to Bugsink grouping key. `scripts/` holds bash wrappers that set up secrets and call the binary or cargo (`live-interop`), and `scripts/cutover` follows that shape.

## Data shape

| Thing | Shape |
|---|---|
| Grouping key | Bugsink joins a custom fingerprint's parts with ` ⋄ `, so `[service, tool, class]` is `service ⋄ tool ⋄ class` (`issues/utils.py`, `get_key_with_mechanism_for_data`, in the 2.6.3 image). |
| Filed | One almanac GitHub issue: its URL, open or closed, and the grouping key read from the header lines of its body (the lines before the first blank line, so sample text can never supply a field). |
| Tracked | One Bugsink issue: its id, friendly id, grouping keys, whether it is resolved, and when it was first seen. |
| Verdict | Per tracked issue: `Resolve` with the closed issues as proof, `Open` with the open issues, `NeverFiled`, or `AlreadyResolved`. |

Closed means closed for any reason. The five brineworks duplicates closed as not planned on 2026-11-09 count.

## Bugsink API (2.6.3, read from the image's `issues/api_views.py`)

- `GET /api/canonical/0/issues/?project=<id>&state=all`, cursor-paginated through `next`.
- `GET /api/canonical/0/issues/<id>/grouping/` lists the grouping keys.
- `POST /api/canonical/0/issue-comments/` with `{"issue": <id>, "comment": <text>}` needs `issues:comment`.
- `POST /api/canonical/0/issues/<id>/resolve/` needs `issues:triage`, and answers 400 when the issue is already resolved.
- Auth is `Authorization: Bearer <40 hex>`.

The comment goes first. A failure between the two leaves an unresolved issue with the comment, and the next `--apply` comments again and resolves. The other order could leave a resolved issue with no proof, and a rerun skips resolved issues.

## Decisions

- **Cutover time.** A constant, `bugsink::CUTOVER`, set from the prod dry run to just after the first full ship's last new issue. It is a fact about prod history, so it belongs in reviewed source rather than in host config, and `tracker-consumer` reads it at compile time. Issue first-seen is ingest time (Appendix A of the program plan), so every replayed issue is first seen inside that ship, and anything first seen after it is new.
- **What the comment links.** The closed GitHub issues only. Bugsink URLs carry the tailnet host, so nothing here prints or stores them.
- **Unmatched issues.** Any almanac issue whose key matches no Bugsink issue is listed with its state. A body written before the `old-shape-error-text` fix can name a class the shipper no longer computes for the same failures.
- **No almanac issue at all.** A Bugsink issue whose fingerprint never crossed the filer's threshold stays unresolved, listed as never filed.

## Results

Local Bugsink 2.6.3, 2026-11-09, with four events whose fingerprints matched closed, open and no almanac issues: `--apply` commented and resolved the two closed ones, and the issue history shows `manual_annotation` with the GitHub links, then `resolved`. A second `--apply` listed both as already resolved and changed nothing. The open and never-filed issues stayed unresolved.

Prod dry run, 2026-11-09 (read only):

| | Count |
|---|---|
| Bugsink issues | 68, all first seen between 03:12:13Z and 03:12:33Z on 2026-11-10 |
| Almanac issues | 44: 21 open, 23 closed |
| Would resolve | 10 |
| Left open, an almanac issue still open | 10, holding all 21 open issues |
| Left open, never filed | 48 |
| Almanac issues matching no Bugsink issue | 3, brineworks #129, #130 and #132 |

The three unmatched issues name class `other` for 2026-10-22 failures that `old-shape-error-text` now classifies as `pg-too-many-clients`. Their fingerprints resolve anyway through the later filings of the same outage.

**For `tracker-consumer`.** The 48 never-filed fingerprints stay unresolved and were first seen before `CUTOVER`. A consumer that skips every issue first seen before `CUTOVER` never files one of them, even when it later crosses its class threshold. The consumer should count only events after `CUTOVER` toward a threshold rather than skip the issue.
